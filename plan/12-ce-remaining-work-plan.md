## 1. 목표와 적용 범위

이미 구현한 무장 조회 제품을 유지하면서 미해석 원천·필드 의미·테스트 이식성·릴리스 판정·원격 운영 검증을 순서대로 해결한다. 새 제품을 처음부터 다시 만들거나 완료 기능을 반복 구현하지 않는다.

사용자의 **“화면검증 제외”** 지시를 계속 적용한다. 게임 화면, 브라우저 렌더링, 스크린샷, Android/iOS 실기기 검사는 이번 실행 범위에 넣지 않는다. 파일 분석·SQL·HTTP·DOM 상태 검사는 수행할 수 있으나 화면 검증의 대체 PASS로 기록하지 않는다.

이번 요청은 저장소 비공개 전환과 계획서 작성이다. 아래 구현·데이터 재생성·배포는 후속 실행 항목이며, 계획서 작성만으로 실행 완료를 표시하지 않는다. GitHub 저장소 비공개와 웹서비스의 접근 공개 여부는 별도로 관리한다.

## 4. 작업별 상세 계획

### R01. 검증 근거와 미완료 항목 정리

1. 최신 코드·프로필·스냅샷·DB·패키지 SHA를 연결한 기준 목록을 작성한다. 이전 보고서를 현재 후보의 통과 근거로 재사용하지 않는다.
2. 문자열 blockers와 별도로 식별 가능한 검증 항목을 설계한다. 항목마다 대상 범위, 상태, 근거 경로, 적용 후보 해시, 재검사 조건, 출시 영향도를 둔다.
3. `PASS`, `FAIL`, `UNRESOLVED`, `EXCLUDED_BY_USER`, 근거 있는 `NOT_APPLICABLE`을 구별한다. 화면 제외 항목은 실패 건수에 섞거나 완료 건수에 더하지 않는다.
4. 11번 계획의 G1~G4 요구와 실제 증거를 매핑하고, 자동 검사 완료와 정식 출시 완료의 차이를 문서화한다.

**산출물:** `reports/remaining-baseline-r4.json`, `docs/release-gates.md`(신규 예정). **완료:** 필수 항목의 미판정 상태가 누락되지 않고 후속 작업·근거로 추적 가능하다.

### R02. 특전 시나리오 32·33 본문 해석

현재 두 파일은 `SN14`/`LWC` wrapper를 찾지 못했다. 기존 분석은 전체 서명 검색, 앞 1,024바이트의 유효 zlib 헤더 검사, 일부 위치의 단일 바이트 XOR 가설 검사까지다. 높은 엔트로피나 우연한 GZIP 접두부는 해독 성공의 근거가 아니다.

1. [기존 조사](../reports/unread-wrappers-24966116.json)를 재사용하고 32·33의 해시를 재확인한다. 같은 가설을 이유 없이 반복하지 않는다.
2. 보존된 KO/JP·관련 DLC 파일을 크기·헤더·블록·버전별로 비교해 파일 family와 후보 wrapper를 좁힌다.
3. 후보 압축 스트림은 실제 종료 조건·출력 경계·본문 구조까지 검사한다. 형식 연구가 필요하면 원 작성자의 공개 코드/문서를 읽고 출처·버전·가설을 기록한다.
4. 형식을 확보한 경우에만 bounded decoder를 추가한다. 손상 길이·잘못된 헤더·최대 출력 초과·참조 이탈에서 명시적으로 실패하게 한다.
5. 해제한 날짜·모드·무장 ID·참조·레코드 수를 독립적으로 검증한 뒤 새 후보에 적재한다. 기존 50개 시나리오 회귀도 확인한다.

**산출물:** wrapper 연구 보고서, 최소 합성 fixture, 파서, 새 catalog/원천 대조 보고서. **완료:** 두 본문과 모든 필수 참조를 검증한다. **미해결 시:** 시도한 가설·배제 근거·필요 자료를 적은 차단 보고서를 남기고 두 시나리오를 미해석 상태로 유지한다. 차단 보고서 작성은 데이터 완료나 출시 허가가 아니다.

설치 파일 수정·게임 재설치·실행 중 메모리 실험을 기본 분석 절차로 삼지 않는다. 새 분석 방식이 실제 필요해지면 대상·복구 방법을 구체화한 뒤 기존 승인 범위와 대조한다.

### R03. 필드 의미·무장·모드·이용 범위 확정

1. raw 신분 5가 관측된 756행을 시나리오·무장 ID·소속·거점별로 정리한다. 관계/상태 변화와 메시지·정적 정의를 대조하되 빈도만으로 신분 라벨을 정하지 않는다.
2. 사실/고대·특전/NPC/임시 슬롯 분류를 ID 범위·이름 휴리스틱과 분리한다. 근거를 확보한 ID 매핑을 만들고 근거 없는 항목은 검토 상태로 남긴다.
3. 일반/전기/튜토리얼 모드 코드를 다른 정적 근거와 교차 확인한다. 별도 모드의 일반 검색 제공 여부는 데이터 범위와 API 계약에 명시한다.
4. 상품 포함, 설치 manifest, 파일 존재, 계정 이용권을 별도 상태로 관리한다. 설치 파일만으로 계정 소유를 확정하지 않는다.
5. 내면 5종과 관계는 추출 완료 상태를 유지하면서 의미 근거·정규화 단위·의형제 파생 규칙을 보강한다. 파서와 동일한 가설을 쓰는 전수 대조를 독립 의미 검증으로 세지 않는다.

**변경 대상:** profile, 필드 사전, 분류 매핑, 검증기, 조회 메타. **완료:** 공개 대상 핵심 필드의 모순이 해결되고 각 분류의 근거 또는 미확정 사유가 존재한다. 화면으로만 확정 가능한 사항은 `EXCLUDED_BY_USER`/미해결로 남긴다.

### R04. 정책 레벨별 효과·전법 설명 보완

1. 현재 제공 중인 정책 이름·설명·구성 정책 ID와 미구현 정량 효과를 분리한다. 공통 원천의 효과 테이블·메시지 참조·레벨 경계·단위·적용 대상을 조사한다.
2. 수치 근거를 확보하면 `policy_level_effect`에 해당하는 명시적 구조를 설계한다. 정책 ID, 레벨, 효과 유형, 값/단위, 조건, 원천 위치를 보존하며 필요 시 스키마 버전을 올린다.
3. 복합 정책의 구성 연결과 실제 중첩·합산 규칙을 구분한다. 규칙이 확인되지 않은 합계·확률·계산값은 제공하지 않는다.
4. 전법 ID를 효과 설명과 연결하고 단일/다중 대상, 적용 조건, 지속·범위 등 확인된 항목만 구조화한다. 설명 전문의 원천이 없으면 결측 상태를 유지한다.
5. 도감·상세 API 및 DOM 상태 로직을 갱신한다. 최소·최대 레벨, 실제 0, 결측, 복합 정책, 설명 누락을 검사한다.

**산출물:** 효과 필드 사전, 스키마/파서/API 변경, 필드별 원천 대조와 경계 테스트. **완료:** 제공 대상 레벨 효과에 출처·단위·조건이 있고 미확정 계산을 수행하지 않는다. 정책 정량 효과 미해결은 상위 계획의 범위 축소 없이 완료로 처리하지 않는다.

### R05. 게임 데이터 없는 새 복제본과 CI

현재 `test_extended.py`, `test_packaging.py`, DOM 테스트 일부는 Git에서 제외된 r3 DB를 직접 참조한다. 기존 32개 통과가 새 GitHub 복제본에서도 그대로 재현된다는 뜻은 아니다.

1. 합성 데이터 계약 검사와 실제 스냅샷 통합 검사를 분리한다. 외부 파일 없이 만들 수 있는 작은 fixture DB로 API·관계·캐시·도감·패키지 실패 조건을 검사한다.
2. 실제 원천이 없는 일반 개발 환경은 통합 검사 제외 사유를 명시한다. 릴리스 검증에서는 원천/DB 부재나 필수 테스트 skip을 실패로 처리한다.
3. 실제 DB 경로를 테스트 설정으로 주입해 특정 r3 파일명 의존을 제거한다. Python·Node 버전과 설치/검사 명령을 기록한다.
4. Python 3.12 배포 대상과 3.14 개발 환경에서 합성 검사를 확인한다. Windows 전용 프로세스 옵션은 분리하고 필요한 CI 환경에서 실행되게 한다.
5. 최소 권한 GitHub Actions를 구성해 합성 단위/API/DOM 검사와 문법 검사를 실행한다. 원천·실제 DB·Steam manifest·백업·인증값을 CI 업로드나 artifact에 넣지 않는다.

**산출물:** 합성 fixture 생성기, 테스트 분리, CI workflow, 새 복제본 실행 문서. **완료:** 게임 파일 없는 깨끗한 복제본에서 정해진 검사가 통과하고, 별도 로컬 통합 검사는 실제 원천 전체를 검사한다. 비공개 repo CI의 이용 한도나 유료 자원이 필요하면 실행 전에 조건을 확인한다.

### R06. 릴리스 판정과 최종 후보 재생성

현재 빌더는 `release_ready=true`를 거부하고, 검증기는 DB 플래그·문자열 blocker·구조 검사를 조합한다. 따라서 blocker 문자열 삭제나 DB 플래그 수동 변경만으로 출시 가능하게 만들지 않는다.

1. R01의 근거 목록에 대상 코드·profile·inventory·후보 해시를 결합한다. 증거 누락·해시 불일치·범위 변경 시 이전 승인 효력을 잃도록 설계한다.
2. 미해석 P0 파일, 필수 필드 의미, 분류 범위, 원천 전수 대조, 필수 통합 검사, 배포 검사를 각각 평가한다. ‘모든 파일 분류됨’과 ‘필수 파일 해석 성공’을 별도 검사로 둔다.
3. 파서/DB → 검증기 → 패키지 검사 → 배포 진입점이 같은 판정 규칙을 사용하게 정리한다. 공개 보류 상태와 정상 공개 상태의 API capability·coverage 응답도 일치시킨다.
4. 코드 변경을 커밋한 뒤 동일 코드 SHA·원천·profile에서 새 후보를 두 번 만든다. 내용 해시와 파일 해시를 각각 비교하고 환경 차이가 발생하면 원인을 기록한다.
5. 기존 r3과 새 후보를 원천 ID로 비교해 필드별 변경·추가·삭제·근거를 검토한다. 새로운 데이터가 늘었다는 이유만으로 이전 행 수에 맞추지 않는다.
6. 전수 대조, 무결성/FK, API·DOM 회귀, 패키지 허용 목록·복원을 검증한다. 테스트 수 자체보다 필수 계약과 실패 조건 충족을 기준으로 판정한다.

**산출물:** 출시 판정 스키마/구현, 코드 SHA가 고정된 후보·재빌드·diff·검증·패키지 보고서. **완료:** 근거 없는 승격이 거부되고 모든 판정 결과를 재현할 수 있다. 화면 제외를 유지한 상태에서는 ‘자동 검사 완료’를 선언할 수 있으나 기존 G3/G4 전체 통과로 바꾸지 않는다.

### R07. 원격 Preview·복구·정식 공개

1. 먼저 로컬에서 후보/패키지 SHA, 미해결 목록, 예상 업로드 범위, 접근 방식, 비용 조건, 복구 대상을 준비한다. 실제 원격 생성/배포 직전의 검토 자료로 사용한다.
2. CE 전용 프로젝트와 접근 정책을 정한다. 비공개 GitHub 저장소라는 이유로 Preview URL도 비공개라고 가정하지 않는다. 미검증 후보를 점검 handler 우회로 공개하지 않는다.
3. 제한된 원격 검토판이 필요하면 검토 환경의 인증·대상 패키지·검증 범위를 별도로 설계하고 확인한다. 정식 공개와 구분된 판정 없이 `release_ready`를 변경하지 않는다.
4. 배포 시점의 공식 문서와 실제 계정 설정으로 Python 지원 버전·번들 한도·라우팅·보호 기능을 재확인한다. 저장소 루트가 아닌 허용 파일 패키지를 배포 대상으로 삼는다.
5. 화면 도구 없이 HTTP로 health, 검색, 상세, 관계, 비교, 도감, JS 모듈 MIME, 오류 응답, DB 직접 다운로드 차단을 검사한다. 배포 버전과 후보 해시를 기록한다.
6. 대표 목록·상세·관계 API를 각 100회 측정한다. 상위 계획의 warm p95 500ms 목표와 비교하고 cold 표본은 별도로 기록한다. 로컬 응답 시간이나 HTTP 측정을 모바일 화면 성능으로 표현하지 않는다.
7. 점검 응답의 실제 배포 ID를 첫 복구 대상으로 확보하고 전환/복구를 검증한다. 정식 공개 조건을 충족한 뒤 같은 검증 아티팩트를 승격하고 직후·1시간 후·다음 날 관찰 결과를 기록한다.

**완료:** 접근 범위·배포 해시·원격 검사·복구·운영 관찰의 실제 증거를 확보한다. 아직 생성하지 않은 프로젝트·URL·배포 ID·검사 결과는 계획값으로만 적는다. 화면 제외 상태의 공개 수용 여부는 공개 직전 별도 결정 사항이다.

### R08. 추가 CE 정적 도감

명승, 역사/시문 이벤트, 공로, 방책을 데이터셋별로 조사한다. 기존 시정 정책과 CE 방책을 같은 테이블이라고 가정하지 않는다.

각 데이터셋에서 파일 family → ID/한국어 명칭/설명/참조 → 원천 근거 → 정적 DB → 도감 API → 검색/상세 DOM 순으로 구현한다. 발동 조건·효과가 런타임에만 존재하면 정적 참조 범위를 명시하고 임의 계산기를 만들지 않는다.

**완료:** 데이터셋별 추출 범위와 누락을 보고하고 원천 대조·유효 참조·API 계약을 통과한 것부터 제공한다. 이 후속 P1 작업 때문에 독립적으로 가능한 핵심 데이터 보완을 지연하지 않는다.

## 5. 사전 확인이 필요한 결정

| 시점 | 구체적으로 준비할 자료 | 사용자 확인이 필요한 경우 |
|---|---|---|
| R02/R03 조사 | 미해결 가설·필요 자료·실험 대상·복구 방법 | 기존 승인 범위를 넘는 설치본 수정, 재설치, 데이터 변경 실험이 필요할 때 |
| R06 범위 조정 | 전체 범위와 축소 범위 비교, 빠지는 데이터/기능, 영향 | 특전 2개·정책 효과 등 P0 미해결을 제외하고 출시하려 할 때 |
| R07 외부 작업 | 구체적인 검토 패키지·프로젝트·접근/비용·복구 계획 | 외부 공개 범위·유료 자원·새 서비스 배포 조건이 아직 승인되지 않았을 때 |
| 화면 검증 정책 | 제외 항목과 자동 검사로 확인할 수 없는 부분 | 화면 검증을 다시 포함하거나, 제외 상태를 수용해 정식 공개하려 할 때 |

이미 승인된 읽기 전용 원천 분석, 별도 CE 코드 수정, 로컬 검사와 새 후보 생성은 후속 구현 지시 범위 안에서 반복 확인하지 않는다. 위 결정이 실제 다음 단계의 조건이 되었을 때 완성된 검토 자료를 제시한다. 질문의 답변 대기 동안 독립 작업은 계속한다. 이 문서 작성 시점에는 위 결정을 미리 요구하지 않는다.

## 6. 실행과 종료 기준

- [ ] R01 근거 목록·검증 상태·출시 영향도 정리
- [ ] R02 특전 wrapper 해석 완료 또는 명시적 차단 기록
- [ ] R03 필드/분류별 의미 근거와 미확정 범위 정리
- [ ] R04 정책 레벨 효과·전법 설명의 원천 확보와 구현
- [ ] R05 합성 CI 및 별도 실제 원천 통합 검사 정착
- [ ] R06 새로운 코드 SHA의 재현 후보·전수 대조·판정·복원 검사
- [ ] R07 원격 검토 조건 확정 후 실제 배포/복구/운영 검증
- [ ] R08 확인된 추가 정적 도감부터 개별 제공

각 작업 보고서는 `대상 SHA / 수행 범위 / 통과·실패·제외 / 미해결 원인 / 다음 조치`를 남긴다. 실패 후보·이전 보고서는 보존하며 Git에는 코드·계획·테스트·비식별 요약만 반영한다. 원천·실제 DB·백업은 기존대로 로컬에 둔다.

다음 구현 착수 시 첫 실행 묶음은 **R01 + R02 1차 분석 + R05 합성 테스트 분리**다. 그 결과로 데이터 연구의 다음 가설과 출시 차단 항목을 갱신한다. 자료 부재로 해결하지 못한 항목과 사용자가 제외한 화면 검증을 완료로 바꾸지 않는다.
