## 1. 계획의 기준과 기존 런북에서 달라지는 결정

10번 메모의 “CE 출시 이후 별도 개발”을 이번 계획의 우선 조건으로 삼는다. 09번의 출시 전 일정은 재사용하지 않고, 실제 착수일부터 단계별 완료 조건으로 진행한다.

CE 출시 여부는 사용자 메모를 작업 전제로 삼았다. 이번 문서 작성에서는 Steam 설치 상태, 현재 상품 구성, 실제 build ID, 한국어 신규 항목을 실측하거나 외부 공식 페이지에서 재확인하지 않았다. 09번에 적힌 날짜·개수·상품 포함 범위는 조사 체크리스트이며 CE DB의 확정값이 아니다.

| 쟁점 | 이번 계획의 결정 | 이유 |
|---|---|---|
| 기존 제품에 CE를 추가할지 | 별도 폴더·저장소·배포 프로젝트에서 CE 제품 개발 | Legacy를 복구 가능한 상태로 유지하고 실험 분리 |
| 기존 DB 재사용 | 비교·회귀 기준으로만 사용, CE 값은 독립 검증 | 기존 원천은 `SUSPECTED_MODIFIED`로 기록되어 있음 |
| 기존 코드 재사용 | 읽기 전용 서버·입력 검증·화면 유틸리티를 선별 이식 | 데이터 가정까지 복사하지 않도록 경계 설정 |
| 시나리오 기본값 | 실제 확보·검증된 CE 일반 시나리오 | 상품명이나 Legacy 목록으로 CE 제공 범위를 추정하지 않음 |
| 내면 수치·정책·관계 | 모두 P0 필수 | 10번의 명시 요구사항 |
| 과거 URL 호환 | 기존 서비스와 도메인에서 그대로 보존 | CE 제품에 PK 데이터를 억지로 섞지 않음 |
| 신규 시스템 도감 | 정적 구조 확인 후 P1 | 핵심 무장 참조 흐름과 원천 정확도를 먼저 완성 |
| 릴리스 저장 | CE 서비스 DB 하나당 활성 릴리스 하나 | 빌드 혼합·복잡한 과거 버전 선택을 피함 |

09번의 백업·원천 계보·후보 DB 검증·롤백 원칙은 유지한다. 다만 기존 `db/sam14.db`를 CE로 승격하는 절차는 사용하지 않는다. CE 후보는 **CE 프로젝트 내부의 서비스 DB**로만 승격한다.

## 2. 제품 목표와 사용자 이용 상황

### 2.1 제품 정의

PC에서 삼국지14 CE를 플레이하는 사용자가 휴대폰으로 무장·정책·개성·관계를 빠르게 확인하는 한국어 참조 웹이다. 화면은 **시나리오 시작 상태**를 제공하며, 진행 중인 세이브의 현재 소속·이동·관계 변화와는 구분한다.

### 2.2 핵심 질문

1. 이 무장의 능력·개성·진형과 내면 수치는 무엇인가?
2. 이 무장의 주의·정책·정책 레벨은 무엇인가?
3. 이 무장이 친애하거나 혐오하는 대상은 누구이며, 반대로 이 무장을 친애하거나 혐오하는 사람은 누구인가?
4. 지금 선택한 CE 시나리오에서 이 무장은 어디에 있고, 미등장이라면 언제 어디에 등장하는가?
5. 내 세력 또는 재야 무장 중 필요한 개성·정책·주의를 가진 사람은 누구인가?
6. 조금 전에 봤던 무장을 검색을 반복하지 않고 다시 열 수 있는가?

### 2.3 첫 출시 성공 기준

- 시나리오 최초 설정 후 이름 검색 → 상세 열기 두 동작으로 핵심 정보를 확인한다.
- 상세 첫 화면에서 소속·상태, 5개 능력, `주의 · 정책 · Lv.` 요약을 확인한다.
- 내면·친애·혐오까지 화면 내 바로가기 한 번으로 이동한다.
- 관계 인물을 따라 탐색한 뒤 이전 인물·검색 결과·스크롤 위치로 돌아온다.
- “없음”, “미확인”, “현재 조건에서 제공하지 않음”이 구분된다.
- 출처와 검증 범위가 확인되지 않은 값을 완성 데이터처럼 표시하지 않는다.

## 3. 현재 구현에서 확인한 출발점

아래는 문서 작성 시 파일을 읽어 확인한 내용이다. 실제 CE 설치본 분석 결과나 기존 오류 전수 진단 결과는 아니다.

| 위치 | 확인한 상태 | CE 재개발 작업 |
|---|---|---|
| `scripts/build_db.py` | Legacy 스냅샷 키·SP1 App ID·시나리오 수 가정 존재 | 프로필·catalog·출력 경로를 명시하는 CE 빌더 |
| `scripts/validate_db.py` | 무장 1,000명, 상태 46,000행, 관계 4,192행 등 고정 | 실측 manifest와 기대 ID 집합으로 검증 |
| `db/schema.sql` | 스키마 버전 3, 여러 CHECK에는 이미 CE 허용 | CE 문자열 추가와 실제 CE 지원을 구분, 새 스키마 버전 4부터 설계 |
| 무장 스키마 | `affinity`는 있으나 요청한 내면 항목 전체 구조는 없음 | 내면 필드 정의·원천 위치·값 사전부터 확정 |
| `officer_policy`·상세 UI | 정책 레벨과 주의는 이미 일부 제공 | CE 값 재검증, 목록·상세에서 한 묶음으로 표현 |
| `scripts/load_reference_data.py` | 정책 레벨 결측을 `or 0` 처리 | 결측과 실제 0을 분리 |
| `scripts/fetch_relationships.py` | 이름·행 순서·상호관계·세력 중첩을 이용한 동명이인 판정 | 내부 식별자 우선, 기존 추정 연결은 검증 대상으로 격리 |
| 관계 적재 | 같은 참고자료 관계를 ORIGINAL·PK에 각각 적재 | CE 관계를 Legacy에서 복제하지 않음 |
| `web/queries.py::_relationships` | 양방향 조회 후 `(type, target_id)`로 중복 제거 | 방향별 응답, 원천·규칙셋·시나리오 범위 적용 |
| `officer-detail.js` | 관계를 유형별로만 묶고 방향을 화면에 반영하지 않음 | “내가 친애 / 나를 친애” 등을 분리 |
| `web/queries.py` | `RULESETS`가 ORIGINAL·PK로 고정 | 공개 프로필·capability 기반 메타 제공 |
| `api/index.py` | 프로젝트 루트의 `db/sam14.db`에 고정 | CE 루트 내부 DB만 사용하도록 설정·경로 검증 |
| `vercel.json` | 함수 `includeFiles`가 `**` | CE 배포 대상 최소화 및 번들 목록 검사 |
| `.gitignore` | `plan/`, `tests/`, 다수 스크립트·DB 설계 파일 제외 | CE 저장소에서 코드·테스트·스키마·계획을 추적하도록 재설계 |

기존 관계 정확도 문제는 원천 오류, 동명이인 매핑, 관계 방향 손실, 시나리오 범위 누락을 나눠 조사한다. 위 구현상 위험만으로 특정 무장 관계가 틀렸다고 확정하지 않는다.

## 4. 프로젝트 분리와 보존

### 4.1 권장 폴더 구조

기존 프로젝트 내부가 아닌 형제 폴더를 사용한다. 아래 CE 경로는 새로 만들 위치에 대한 제안이며, 현재 생성된 상태가 아니다.

```text
C:/Users/jskim/Documents/projects/02-build/
├─ 001-sam14-db/                 # 기존 Legacy 제품, 기존 운영 연결 유지
│  └─ .artifacts/releases/      # Legacy 코드·DB·설정 보존본
└─ 002-sam14-ce/                 # CE 전용 프로젝트와 별도 Git 저장소
   ├─ README.md
   ├─ plan/                     # 결정 기록·분석 결과·작업로그
   ├─ profiles/                 # build·catalog·공개 범위 설정
   ├─ catalog/                  # 상품·팩·시나리오 식별 목록
   ├─ extractors/               # 파일 family별 읽기 전용 파서
   ├─ scripts/                  # inventory·diff·build·validate·run
   ├─ db/                       # schema.sql·후보 DB·서비스 DB
   ├─ api/                      # CE 배포 진입점
   ├─ web/                      # CE API 쿼리와 모바일 UI
   ├─ tests/fixtures/           # 합성 fixture와 검증된 최소 사례
   ├─ reports/                 # 비식별·배포 가능한 검증 요약
   └─ .artifacts/               # 원천·중간 산출물·릴리스 보존본, Git 제외
```

실제 폴더 생성 전에 대상 경로의 존재 여부를 확인하고, 이미 다른 작업이 있다면 덮어쓰지 않는다. 전체 디렉터리를 복제하며 `.git`, `.vercel`, 비밀값, 원본 게임 파일까지 가져오는 방식은 사용하지 않는다.

### 4.2 Legacy 보존 작업

1. Git SHA, `git status`, 실행 환경, DB SHA-256, 스키마·catalog·보고서, 운영 URL과 배포 ID를 기록한다.
2. 추적 파일뿐 아니라 Git에서 제외된 파서·계획·테스트·원천 메타도 별도 보존한다. `git archive`만으로 백업 완료 처리하지 않는다.
3. 미커밋 변경은 수정 내용과 함께 보존하고 기준 커밋과 구분한다. 작성 시점에는 `web/static/notion-theme.css` 변경이 있으므로 누락하지 않는다.
4. 게임 설치본·Steam manifest의 기존 보존 여부를 확인한다. 업데이트 전 파일을 잃었다면 현재 설치본을 Legacy 원천이라고 이름 붙이지 않는다.
5. 백업 파일 해시 확인, 별도 위치의 읽기 전용 로컬 실행, 대표 기존 URL 확인으로 복원 가능성을 검증한다.
6. 백업은 로컬 외 별도 저장장치에도 한 벌 보존한다. 용량 부족 시 보존 범위와 누락을 기록한다.

Legacy 원천 부재는 “Legacy 전체 diff 가능” 판정을 막는다. 그러나 독립된 깨끗한 CE 원천을 확보하면 CE 분석은 진행할 수 있다. 이때 Legacy 비교의 한계를 기록하고 CE 자체의 검증 기준은 낮추지 않는다.

### 4.3 분리 완료 조건

- CE 빌더가 기존 프로젝트 경로 또는 기존 DB를 출력 대상으로 받으면 실패한다.
- CE DB 기본 경로·로컬 포트·설정·브라우저 저장 키가 Legacy와 분리된다.
- 새 Vercel 프로젝트는 CE 저장소만 연결하며 기존 배포 프로젝트 설정을 복사하지 않는다.
- CE 작업 전후 Legacy 서비스 DB 해시가 동일하다.
- 공개 원천이 아닌 게임 바이너리·초상화·메시지 전문·라이선스 개인정보가 Git·배포물에 없다.

## 5. 범위와 우선순위

| 우선순위 | 제공 범위 | 출시 기준 |
|---|---|---|
| P0 필수 | 원천 스냅샷·프로필·catalog·무장 식별자 | 재현 가능한 빌드와 행/필드 계보 |
| P0 필수 | 검증된 CE 일반 시나리오와 무장 시작 상태 | 공개 시나리오별 기대 ID 집합 전수 일치 |
| P0 필수 | 능력·개성·진형·주의·정책·레벨 | CE 원천 검증과 복합 검색 |
| P0 필수 | 의리·외교·한조·야망·호전 등 내면 정보 | 실제 존재·의미·범위 확인, 필드별 검증 |
| P0 필수 | 친애·혐오, 기존 혼인·의형제 기능 | 방향·대상 ID·적용 범위 검증 |
| P0 필수 | 모바일 탐색·상세·최근 조회·즐겨찾기·URL 복원 | 대표 실기기 흐름 통과 |
| P0 필수 | coverage·성능·독립 배포·복구 기록 | 릴리스 게이트 통과 |
| P1 | 2~3명 비교, 저장 검색 조건, 등장 후보 모아보기 | P0 안정화 후 사용자 과업 기준 검증 |
| P1 | 전법 보유 관계의 누락 보완, CE 신규 정적 도감 | 원천 확보된 데이터셋별 공개 |
| P1 | 명승·역사/시문 이벤트·공로·방책 등 | 확인된 실제 구조와 한국어 명칭만 사용 |
| P2 | 전체 오프라인 조회, 상세 지도, 동적 시스템 해설·계산 | 정확한 규칙·유지 비용 확인 후 별도 계획 |

P0 내면·정책·관계 요구를 미확인 배지로 대체하고 정식 완료 처리하지 않는다. 공개 대상에서 필요한 핵심 필드가 해결되지 않으면 정식 출시는 Hold이며, 범위를 명시한 내부 Preview만 제공한다. 실제 게임에서 적용되지 않는 필드는 근거와 함께 `NOT_APPLICABLE`로 완료 판정할 수 있다.

로그인, 게임 파일 쓰기, 세이브 자동 추적, 실시간 게임 연동, 임의 성공 확률 계산은 이번 재개발 범위에 포함하지 않는다.

## 6. CE 원천을 처음부터 분석하는 절차

### 6.1 원천 확보와 증거

1. 현재 라이선스·설치 완료 상태·한국어 언어 설정·실제 Steam build ID를 확인한다.
2. 게임과 Steam이 파일을 쓰지 않는 상태에서 설치본을 보존한다.
3. 상대 경로, 크기, SHA-256, 파일 시그니처, 캡처 시각을 전체 inventory에 기록한다.
4. snapshot의 clean 상태는 검증 결과로 정한다. 새 폴더에 복사했다는 사실만으로 `CLEAN` 처리하지 않는다.
5. 실제 설치 목록과 한국어 게임 화면의 일반 시나리오·별도 모드·특전·신규 무장 목록을 대조한다.
6. 상품 소유, 번들 포함, 설치, 추출, 공개 가능 여부를 각각 기록한다. 상위 패스 소유만으로 모든 child DLC 설치를 인정하지 않는다.

09번의 SP2 일반 시나리오와 `조조의 오산`, `패기웅심` 등은 확인 대상에 포함한다. 개수·이름·획득 가능 기간은 실제 자료와 대조해 확정한다. 미소유 콘텐츠는 catalog에 남기되 내부 ID나 데이터를 지어내지 않는다.

### 6.2 파일 구조 분석

- 기존 inventory와 비교 가능하면 `ADDED / CHANGED / UNCHANGED / REMOVED`를 생성한다.
- 비교 원천이 없으면 초기 CE inventory로 기록하고 `UNCHANGED`를 추정하지 않는다.
- 헤더·레코드 길이·인덱스·문자 인코딩·참조 포인터·결측 sentinel을 파일 family별로 조사한다.
- 원천의 무장·시나리오·정책·관계 ID를 독립적으로 추출하고 ID 매핑표를 만든다.
- 구조 가설마다 최소 정상 사례, 경계값, 결측, 복수 항목, 동명이인 사례를 확인한다.
- 알 수 없는 family·길이·참조값에서는 파서가 명확히 실패하게 한다. 기존 PK 포맷으로 강제 해석하지 않는다.
- 분석용 출력은 offset·record index·raw 값과 해석값을 함께 저장한다.

파일 처리 상태는 `REUSED_VERIFIED`, `EXTRACTED`, `CATALOG_ONLY`, `EXCLUDED`, `FAILED`로 구분하고 사유를 남긴다. 전체 inventory의 게임 데이터 밖 파일은 범주별 제외 근거를 기록하며, P0 대상 파일은 미처리·실패 0건을 요구한다.

### 6.3 정규화와 재현

```text
불변 CE 원천 스냅샷
  → 전체 inventory + 파일 분류
  → family별 raw 레코드 + 위치 증거
  → 식별자 매핑 + 정규화
  → staging 검증 + 불일치 목록
  → 별도 후보 SQLite DB
  → 전수 검증 + 게임 화면 교차 확인
  → CE Preview → CE 정식 배포
```

새 도구는 `inventory_install.py`, `diff_install_inventory.py`, `build_db.py`, `validate_db.py`, `compare_release.py`로 구분한다. CLI에는 `--source-root`, `--profile`, `--catalog`, `--output`, `--report`를 설계하되 아래 이름은 구현 예정 인터페이스이며 현재 실행 가능한 명령으로 취급하지 않는다.

빌더는 명시한 후보 파일에만 쓰고 기존 출력 덮어쓰기를 기본 거부한다. 트랜잭션 내 적재 후 검증 실패 시 임시 후보를 폐기하며, 원천·현재 서비스 DB는 수정하지 않는다. 같은 원천·파서·프로필의 재빌드는 시각 메타를 제외한 정규화 내용 해시가 같아야 한다. 배포 아티팩트 자체의 SHA-256은 별도로 보존한다.

## 7. 핵심 데이터 재설계

### 7.1 식별자·규칙셋·시나리오

- 게임 내부 ID와 서비스 공개 ID를 분리하고 `(snapshot, entity_type, source_internal_id)` 매핑을 유지한다.
- 이름만으로 Legacy와 CE 무장을 결합하지 않는다. 내부 ID도 빌드 간 안정성을 검증한 뒤 연결한다.
- 확인된 동일 시나리오 정체성과 CE 변형을 분리한다. 이름·연월만으로 동일성을 확정하지 않는다.
- CE 상품 식별자와 데이터 규칙셋을 분리한다. PK 파일명이 유지돼도 CE가 PK와 동일하다는 증거로 쓰지 않는다.
- 최초 분석에서는 CE 규칙셋 후보를 사용하고 파일 diff·게임 설정·시스템 활성 범위로 최종 결정한다.
- UI는 CE 제품 문맥을 기본으로 삼고 불필요한 ORIGINAL/PK 토글을 제거한다. 실제 구분 가능한 CE 내부 모드만 제공한다.
- 일반 검색은 검증된 일반 시나리오만 포함한다. 전기제패·튜토리얼은 별도 catalog로 분리한다.

### 7.2 내면 수치

의리·외교·한조·야망·호전은 사용자가 요청한 조사 항목이다. 실제 CE 필드명, 수치형 여부, 한국어 명칭, 허용 범위는 원천 확인 후 확정한다. 예를 들어 “외교”가 독립 필드인지 다른 성향의 설명인지 아직 가정하지 않는다.

| 필드 정의에 필요한 항목 | 기록 내용 |
|---|---|
| 기술 식별자 | 의미 확인 후 고정한 영문 key |
| 화면 명칭 | 한국어 게임 기준 이름과 별칭 |
| 원천 | 파일·record·offset 또는 확인 화면 |
| 자료형 | 정수 / enum / boolean / 구조형 |
| 값 규칙 | 최소·최대·단위·sentinel·enum 코드표 |
| 적용 범위 | 무장 기본값 / 규칙셋 / 시나리오 시작값 / 런타임 |
| 해석 근거 | 검증 표본·반례·신뢰도·확인 일자 |

구조가 확정된 스칼라는 `officer_personality`의 명시적 typed 열로 관리한다. 같은 값이 시나리오별로 달라지는 증거가 있을 때만 별도 시작값 테이블을 추가한다. 모든 미해석 값을 무제한 key-value 테이블로 서비스하지 않는다.

`affinity`라는 이름의 기존 상성값과 친애 관계는 다른 개념으로 취급한다. 런타임 충성도 등도 내면 기본값과 섞지 않는다. 원천이 enum이면 확인된 코드와 라벨을 보여주고 임의로 0~100 점수나 성공 확률로 환산하지 않는다.

표시 상태는 `VERIFIED`, `UNKNOWN`, `NOT_APPLICABLE`, `CONFLICT`로 분리한다. 값 0은 실제 0이며, 미확인은 `null`과 상태로 반환한다. 충돌은 staging에서 보존·해결하며 검증 완료값을 임의 선택하지 않는다.

### 7.3 주의·정책·레벨

- 주의와 정책 마스터, 무장별 정책 보유·레벨, 레벨별 효과를 구분한다.
- `왕도 · 호적정비 · Lv.3`처럼 목록과 상세에 함께 배치한다. 이는 요청한 표현 예시이며 특정 무장의 확정 데이터가 아니다.
- 정책이 여러 개인 구조라면 전부 반환하고 표시 우선순위를 정의한다.
- 레벨 결측을 `0`으로 바꾸지 않는다. 기존 1~10 범위를 CE 사실로 재사용하지 않는다.
- 레벨 효과는 해당 무장의 레벨을 먼저 보여주고 전체 레벨표는 펼쳐보기로 제공한다.
- 주의·정책·최소 레벨 필터를 조합할 수 있어야 한다. enum/레벨 범위는 검증된 메타에서 가져온다.
- 기존 시정 정책과 CE 방책이 다른 개념이면 독립 테이블·별도 화면으로 유지한다.

### 7.4 친애·혐오 재구축

관계는 기본적으로 `A → B`의 방향을 보존한다. 원천에서 확인된 관계만 적재하고 역방향을 자동 생성하지 않는다.

1. 원천 ID와 관계 slot을 직접 추출한다. 이름만 제공되는 보조자료는 후보 생성용으로 제한한다.
2. 동명이인별 매핑 증거를 기록한다. 동일 세력·상호관계·행 순서만으로 확정하지 않는다.
3. 공통 관계와 시나리오별 관계가 실제로 있는지 조사한다. 시나리오 관계가 추가인지 전체 대체인지 확인하기 전 합치지 않는다.
4. 시나리오별 목록이 전체 대체이면 “확인된 빈 목록”도 공통 관계를 지우는 override로 표현한다. 행이 없다는 이유로 공통 목록을 되살리지 않는다.
5. 관계 scope의 유일성을 DB 제약으로 보장한다. nullable 시나리오를 포함한 UNIQUE만으로 중복을 막는 설계는 피한다.
6. 원천 전수 관계 집합과 정규화·DB 집합을 비교하고, 추가·삭제·대상 변경·방향 변경을 보고한다.
7. 혼인·의형제의 대칭 여부도 실제 구조에 따라 결정한다. 친애·혐오의 규칙을 그대로 적용하지 않는다.

상세 화면의 네 기본 구역:

- **내가 친애하는 무장**: 현재 무장 → 대상
- **나를 친애하는 무장**: 대상 → 현재 무장
- **내가 혐오하는 무장**: 현재 무장 → 대상
- **나를 혐오하는 무장**: 대상 → 현재 무장

양방향이면 두 구역에 각각 나타나거나 명시적인 “서로 친애” 표시를 사용한다. 방향 정보는 중복 제거 과정에서 사라지면 안 된다. 수록 여부를 검증한 빈 목록만 “없음”으로 표시하고, 미검증은 “확인 중”으로 표시한다.

### 7.5 CE 스키마 v4의 논리 테이블

다음은 설계 후보이며 파일 구조 분석 후 DDL을 확정한다.

| 테이블/묶음 | 책임·주요 제약 |
|---|---|
| `release_profile`, `source_snapshot`, `source_file` | 활성 프로필 1개, build·inventory·원천 신뢰 상태 |
| `product_edition`, `content_pack`, 연결 테이블 | 판매 상품·전달 팩·보유/설치 사실 분리 |
| `scenario`, `scenario_variant`, `ruleset` | 정체성·변형·공개 가능 조합 |
| `entity_source_map` | 원천 ID와 서비스 ID의 명시적 연결 |
| `officer`, `officer_version` | 정체성과 활성 규칙셋별 무장 값 |
| `officer_personality`, enum 사전 | 검증된 내면 필드와 의미 |
| `doctrine`, `policy`, `officer_policy`, `policy_level_effect` | 주의·정책·레벨·효과 |
| 개성·진형·전법 사전과 보유 연결 | 규칙셋 내 유효 참조·slot 검증 |
| `scenario_force`, `scenario_officer_state` | 세력·위치·상태·등장 시기 |
| `relationship_scope`, `relationship_edge` | non-null scope, 방향, 유형, 빈 override 포함 |
| `evidence`, `field_verification`, `dataset_coverage` | 행/필드 증거·검증 상태·기대/실제 범위 |

외래키 존재뿐 아니라 연결된 무장·정책·도시·세력의 규칙셋과 시나리오가 같은지도 검증한다. 구체적인 FK·복합 UNIQUE·CHECK 설계는 schema 결정 기록에 남긴다.

모바일 기본 결과는 카드로 구성하고, 데스크톱에서는 표와 상세 분할 패널을 사용한다. 개성 전체·효과 설명은 상세에서 제공하여 목록 카드가 과도하게 길어지지 않게 한다.

### 8.3 게임 중 참조를 편하게 하는 수정사항

| 기능 | 우선순위 | 구체적인 동작 |
|---|---|---|
| 시나리오·내 세력 기억 | P0 | 다음 방문에도 유지, 상단에 적용 문맥 표시 |
| 이름 검색 자동완성 | P0 | 동명이인은 검증된 구분 정보 제공, 한글 입력 조합 중 요청 억제 |
| 상세 섹션 바로가기 | P0 | `요약 / 내면 / 관계 / 전투` 앵커, 선택 시 스크롤 |
| 탐색 복귀 | P0 | 관계 A→B→C 뒤로가기, 검색·필터·목록 위치 보존 |
| 최근 조회·즐겨찾기 | P0 | 기기 내 저장, 1회 탭으로 재조회, 개별 삭제·초기화 |
| 야간 읽기 | P0 | 시스템 테마 + 사용자 선택, 의미는 색상 외 텍스트로 표시 |
| 연결 지연·끊김 대응 | P0 | 현재 표시 유지·재시도, 오래된 캐시임을 명시 |
| 비교 | P1 | 2명 기본·3명까지, 내면·정책·개성 차이 확인 |
| 저장 검색 | P1 | “내 세력 + 특정 정책” 등을 이름 붙여 저장 |
| 등장 후보 | P1 | 시작 시점 기준 등장 연월 정렬, 현재 진행 상태로 오인하지 않게 안내 |
| PC→휴대폰 이어보기 | P1 | 현재 조건 링크·QR 공유, 별도 로그인 없이 열기 |

자동 화면 켜짐 유지, 불필요한 애니메이션, 큰 초상화 우선 배치는 기본값으로 두지 않는다. 작은 화면에서 읽는 정보와 이동 횟수를 우선한다.

### 8.4 상태·접근성·반응형 규칙

- URL에 명시한 조건이 기기 저장값보다 우선하고, 그다음 저장값, 마지막으로 공개 프로필 기본값을 적용한다.
- 시나리오 변경 시 더 이상 유효하지 않은 세력 필터를 해제하고 이유를 알린다.
- 즐겨찾기는 공개 ID로 저장하고 릴리스 변경으로 대상을 찾지 못하면 조용히 다른 인물로 바꾸지 않는다.
- 저장 키에 CE 제품·저장 형식 버전을 포함하고 ID 변환이 불확실하면 재선택을 안내한다.
- 360·390·430px에서 본문 가로 스크롤이 없어야 한다. 긴 이름·큰 글자·가상 키보드·safe area를 점검한다.
- 터치 영역은 최소 44×44 CSS px를 제품 기준으로 사용한다.
- 상세를 열고 닫을 때 포커스를 관리하고, 키보드·스크린리더에서 이름·상태·관계 방향을 읽을 수 있게 한다.
- `loading / empty / error / partial`을 구분하고 정보 미수록을 결과 0건으로 숨기지 않는다.

## 9. API·구현 구조

### 9.1 기술 선택

기존의 Python + SQLite + HTML/CSS + Vanilla JavaScript를 기본으로 유지한다. 원천 재분석과 데이터 검증이 주요 위험이므로 프레임워크 전면 교체를 선행 조건으로 만들지 않는다. CE 프로젝트에서 데이터 추출·정규화·조회·화면을 분리하고 로컬 서버와 배포 진입점은 동일 조회 서비스를 사용한다.

### 9.2 CE API 초안

별도 호스트의 `/api/v1`을 사용한다. 기존 Legacy `/api/*`는 기존 호스트에서 유지한다.

| API | 책임 |
|---|---|
| `GET /api/v1/health` | 연결·스키마·read-only·활성 릴리스 확인 |
| `GET /api/v1/meta` | 기본 시나리오·capabilities·필터·enum |
| `GET /api/v1/coverage` | 데이터셋·시나리오·필드별 완전성 |
| `GET /api/v1/scenarios` | CE 시나리오와 공개/미소유/미확인 상태 |
| `GET /api/v1/officers` | 이름·시나리오·상태·세력·주의·정책·레벨·개성 검색 |
| `GET /api/v1/officers/{id}` | 내면·정책·관계까지 한 번에 받는 상세 |
| `GET /api/v1/officers/{id}/relationships` | 방향·유형·시나리오별 관계 탐색 |
| `GET /api/v1/traits`, `/policies`, `/formations` | 도감·필터 메타 |

목록·상세는 모두 같은 공개 프로필을 선택한다. 필수 시나리오 문맥이 없으면 `/meta`의 명시적 기본값을 적용하며, 없는 조합을 임의로 PK나 다른 시나리오로 대체하지 않는다.

상세의 `personality`는 필드별 `value / label / verification_status`를 포함한다. `policies`는 주의·정책·레벨의 연결을 잃지 않는다. `relationships`는 outgoing·incoming을 독립 배열로 반환하고 각 배열의 검증 상태도 제공한다. 응답 공통 메타에는 `release_id`, `scenario_id`, `data_as_of`, `coverage_status`를 둔다.

### 9.3 쿼리·오류·캐시

- SQLite URI `mode=ro`, `PRAGMA query_only`, 매개변수 바인딩, 정렬 허용 목록을 유지한다.
- 복수 개성·관계 필터는 `EXISTS` 등으로 행 곱셈과 중복 결과를 방지한다.
- 잘못된 입력은 400, 없는 대상은 404, 내부 오류는 경로·SQL을 숨긴 오류 코드로 반환한다.
- 검색은 약 150ms debounce와 이전 요청 취소를 적용하고 늦은 응답이 새 조건을 덮어쓰지 못하게 한다.
- 메모리/브라우저 캐시는 릴리스·시나리오·필터를 키에 포함한다. 릴리스 변경 시 이전 결과를 혼합하지 않는다.
- P0는 브라우저 상태 저장과 제한적인 조회 캐시까지만 구현한다. 전체 오프라인 DB·서비스 워커는 P2로 분리한다.
- health 요청마다 무거운 전체 무결성 검사를 반복하지 않는다. 전체 검사는 빌드·승격 게이트에서 실행한다.

## 10. 검증 및 인수 기준

### 10.1 데이터 게이트

| 검증 | 합격 조건 |
|---|---|
| 원천 추적 | P0 공개값이 snapshot·file·record 또는 교차 검증 증거로 연결 |
| 전체 파일 분류 | 모든 inventory 항목에 처리 또는 제외 근거 존재 |
| 공개 시나리오 | 시나리오별 상태의 무장 ID 집합이 해당 모드의 기대 집합과 정확히 일치 |
| 무장 범위 | 신규·고대·비활성·NPC 처리 정책과 분모를 명시, 1,000명 고정 금지 |
| 상태 | 공개 시나리오의 `UNKNOWN` 0, 소속·위치 참조 유효 |
| 내면 | 요청 필드의 실제 정의 확정, 공개 대상의 미해결 충돌·필수 미확인 0 |
| 정책 | 주의·정책·레벨 연결 오류 0, 결측→0 변환 0 |
| 관계 | ID 오연결·중복·자기관계·방향 손실 0, 원천 관계 집합과 일치 |
| scope | 다른 시나리오·규칙셋의 관계나 상태가 섞이는 사례 0 |
| DB | `integrity_check=ok`, FK 위반 0, UNIQUE 위반 0 |
| 재현성 | 동일 입력의 정규화 내용 해시 동일 |
| diff | 이전 DB와 비교 가능한 모든 변경에 분류·사유, 비교 불가 범위 명시 |

모든 정규화 행과 원천 레코드를 자동 비교한다. 별도로 한국어 게임 화면을 이용해 알려진 무장, 신규 무장, 내면 경계값, 단방향·양방향 관계, 동명이인, 각 시나리오 시작 상태를 교차 확인한다. 화면 표본은 전수 검사의 대체가 아니라 파서 해석을 확인하는 보완이다.

### 10.2 필수 회귀 사례

- 관계 `A→B`만 있을 때 A의 outgoing과 B의 incoming에만 나타난다.
- `A→B`, `B→A`가 모두 있어도 방향 두 개가 손실되지 않는다.
- 친애와 혐오가 충돌할 때 자동 덮어쓰기 없이 검토 대상이 된다.
- 동명이인 대상과 시나리오 override, 확인된 빈 override를 정확히 조회한다.
- 내면 실제 0, 미확인 null, enum 0, 적용 대상 아님을 각각 구분한다.
- 정책 레벨 결측·경계값·복수 정책을 정확히 반환한다.
- 신규 무장 수 증가, 비연속 내부 ID, 없는 참조 ID를 처리한다.
- 시나리오 전환 시 세력·관계·즐겨찾기 데이터가 이전 조건에 머물지 않는다.
- 미소유·미설치·미추출 콘텐츠가 완성된 공개 시나리오로 노출되지 않는다.
- 검색 입력·정렬·페이지 크기 검증과 SQL/경로 비노출을 유지한다.

### 10.4 성능 목표와 측정법

아래 수치는 측정 전 제품 목표다. 실제 공개 데이터 규모와 배포 환경을 확보한 후 기준을 확정하고 변경 근거를 남긴다.

- Preview에서 대표 목록·상세·관계 API 각 100회 측정, warm p95 500ms 이내를 목표로 한다.
- 별도 cold 요청 표본의 응답시간·오류를 보고하고 warm 결과에 섞지 않는다. 초기 cold 목표는 2초 이내다.
- 휴대폰 Wi-Fi/모바일망을 구분해 입력 종료→결과 표시 p95 1초 이내, 초기 주요 화면 2.5초 이내를 목표로 한다.
- 필터 최대 조합·관계가 많은 무장·가장 큰 시나리오로 느린 경로를 확인한다.
- 배포 번들·DB 크기와 실제 플랫폼 제한을 기록하고 한도를 넘으면 Go를 차단한다. 플랫폼 제한 수치는 구현 시 공식 문서로 확인한다.

## 12. 배포와 롤백

1. CE 서비스용 DB는 검증된 후보의 바이트 단위 사본으로 만들고 SHA-256을 확인한다.
2. CE 전용 프로젝트에 Preview를 생성한다. 빌드 보고서의 Git SHA·DB SHA·inventory SHA·schema·profile을 함께 기록한다.
3. 번들에 CE 코드·서비스 DB·필수 정적 파일만 있는지 확인한다. `.artifacts`, 원천, 실험 DB, 개인정보는 제외한다.
4. 공개 대상과 동일한 Preview에서 `/health`, `/coverage`, 대표 검색, 관계 방향, 공유 URL, 모바일 흐름을 확인한다.
5. 가능한 경우 검증한 동일 배포를 승격한다. 재빌드가 필요한 배포 방식이면 결과 해시와 smoke test를 다시 확인한다.
6. 첫 CE 공개는 별도 URL에서 진행한다. 기존 도메인을 CE로 교체하거나 PK URL을 CE로 자동 리디렉션하지 않는다.
7. 직후·1시간 후·다음 날 오류와 대표 과업을 확인한다. 관찰 시각과 결과를 릴리스 기록에 남긴다.

지속적인 health/5xx 오류, 다른 시나리오 데이터 혼입, 관계 방향 손실, 필수 필드 누락, 사용을 막는 성능 회귀가 생기면 CE 공개를 중단하거나 직전 정상 CE 배포로 되돌린다.

첫 CE 배포에는 직전 정상 CE 배포가 없으므로, 출시 전 검증한 점검 안내 배포를 복구 대상으로 준비한다. Legacy 서비스 주소를 대안으로 안내하되 CE 데이터라고 표시하지 않는다. 실제 플랫폼의 롤백·승격 기능과 플랜 제약은 구현 시 확인하고 확인된 절차만 운영 문서에 넣는다.

## 13. 위험·중단 조건·대응

| 위험 | 조기 확인 방법 | 대응 |
|---|---|---|
| 원천 변조 또는 업데이트 중 캡처 | 파일 해시·manifest·게임/Steam 상태 확인 | 새 snapshot 확보, 미확인 원천은 확정 근거로 승격하지 않음 |
| CE 구조 전면 변경 | M1 파일 family·레코드 실측 | 파서 연구 일정 재산정, G1에서 추출 가능 범위 결정 |
| 내면 필드 의미 불명 | 값 분포·게임 화면·표본 대조 | 매핑 가설 기록, 해결 전 정식 P0 Hold |
| 친애·혐오 해석 오류 | 단방향·동명이인·scope 전수 사례 | raw→정규화→API→UI 각 단계 diff |
| 미소유 DLC | 라이선스·설치·게임 목록 대조 | catalog-only 유지, 공개 범위와 분모 명시 |
| Legacy 원천 부재 | M0 보존 조사 | 비교 가능 범위 제한, CE 독립 원천 검증 강화 |
| CE 개발이 Legacy에 영향 | 경로·배포 프로젝트·해시 확인 | 형제 폴더·별도 Git·출력 경로 차단 |
| 모바일 정보 과밀 | 실제 게임 중 U01~U09 수행 | 첫 화면 요약·섹션 바로가기·상세 펼침 조정 |
| 작업 중 게임 재업데이트 | build와 inventory 해시 변화 | 기존 snapshot 고정, 새 snapshot으로 차기 후보 작성 |
| DB/배포 번들 증가 | M2부터 크기 기록·Preview 측정 | 불필요 파일 제외, 쿼리·응답 최적화 후 재검증 |

**Go:** G0~G4 통과, 핵심 필드·관계 충돌 0, 복구 대상 확인.

**Hold:** 설치·원천·필수 필드·UI·성능의 해결 가능한 미완료가 존재. Legacy 운영을 유지하고 CE는 내부 Preview로 제한.

**범위 재계획:** P0 핵심 요구의 신뢰성 있는 추출이 불가능하거나 원천 근거가 지속적으로 확보되지 않음. 완료로 선언하지 않고 원인·확보 가능한 범위·추가 작업량을 제시한다.

## 14. 최종 산출물과 완료 정의

### 14.1 산출물

- Legacy 복원 가능한 코드·DB·설정·작업 파일 백업과 해시 목록
- 독립 CE 프로젝트, 실행·개발·배포 README
- 비공개 CE 원천 스냅샷·inventory·라이선스/설치 증거
- 파일 구조 분석서·필드 사전·ID 매핑·규칙셋 판정 기록
- catalog·스키마 v4·파서·빌더·검증 도구·fixture
- CE 후보/서비스 DB·build report·coverage·diff report
- 모바일 중심 UI·읽기 API·인수/실기기/성능 보고서
- CE Preview/정식/복구 배포 정보와 운영 관찰 기록

### 14.2 완료 체크리스트

- [ ] 기존 제품의 미커밋·Git 제외 파일까지 보존했고 복구 가능하다.
- [ ] CE 개발·DB·배포가 Legacy와 분리되어 있다.
- [ ] 실제 CE build·원천·소유·설치·공개 범위가 문서화되어 있다.
- [ ] 모든 공개 시나리오의 시작 상태가 기대 ID 집합과 일치한다.
- [ ] 요청한 내면 항목의 정의·값·범위·검증 상태가 확정되었다.
- [ ] 주의·정책·레벨을 목록과 상세에서 함께 확인한다.
- [ ] 친애·혐오 방향과 동명이인·시나리오 범위가 정확하다.
- [ ] 모바일 최근 조회·즐겨찾기·검색 복귀·공유 URL이 동작한다.
- [ ] 핵심 데이터 미확인을 완성 데이터로 숨기지 않는다.
- [ ] 전수 검증·게임 화면 교차 확인·API·실기기·성능 게이트를 통과했다.
- [ ] 검증한 아티팩트와 실제 배포의 버전·해시가 일치한다.
- [ ] 첫 배포 복구 절차와 공개 후 관찰 결과를 기록했다.

### 14.3 다음 착수 순서

첫 작업은 **CE-001 Legacy 보존 → CE-002 독립 폴더 구성 → CE-003 현재 CE 원천 확보**다. 이후 M1에서 실제 파일 구조와 내면·관계 추출 가능성을 확인한 뒤 스키마·일정을 확정한다. 이번 문서 작성은 계획 수립 범위이며 기존 코드·DB·배포 변경이나 CE 폴더 생성은 수행하지 않았다.
